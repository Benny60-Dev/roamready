| 13 | **Map click-to-popup centering** — pan camera so clicked stop's popup is fully visible | **DONE** | `focusStop` useCallback in [client/src/pages/trips/TripMapPage.tsx](client/src/pages/trips/TripMapPage.tsx) wraps `setSelectedStop` + `mapInstance.panTo({ lat, lng })` + `mapInstance.panBy(0, -offset)`. Wired at the three click sites: marker `addListener('click', …)`, sidebar row `onClick`, and sidebar row `onKeyDown` (Enter/Space). The `setSelectedStop` calls in `handleUpdateNights` (nights stepper) and the popup close button are deliberately left as raw state updates — they don't need a camera move. The popup is an `<OverlayViewF>` geographically anchored to the stop, so without a camera move sidebar-list clicks on off-screen stops produced no visible feedback (popup rendered outside the viewport) and clicks on markers near map edges clipped the ~260px popup card above the marker. **History — sign and magnitude correction:** the initial fix passed `panBy(0, +offset)` with `offset = clamp(80, mapH/3.5, 160)`. The sign was inverted (Google's `panBy` +y moves the map *center* south, which makes markers appear to move *north* on screen — the previous fix was nudging clicked markers into the upper third instead of the lower third, so the Crested Butte case clipped the popup off the top edge instead of fixing it). Tightened to: `NEEDED_CLEARANCE_PX = 296 (full-variant card) + 36 (triangle gap) + 24 (breathing) = 356`; `offset = min(max(NEEDED_CLEARANCE_PX - mapH/2, 80), mapH * 0.3)`; `panBy(0, -offset)`. On a 550px desktop map: offset=81, marker lands at y=356, clearance above ≈ 356 (fits full-variant popup with 24px breathing). On a 340px mobile map: offset caps at 102, marker lands at y=272, full-variant popup clips by ~60px at top in worst case (mathematically unavoidable on small mobile + maximum content) but marker stays visible — typical content fits cleanly. Already-centered clicks get a modest ~80px downward nudge that keeps the popup top unclipped. First-load races (mapInstance null) safely no-op via the `if (mapInstance && …)` guard. | — |

## How to maintain this file

- When you ship a fix that changes an item's status here, edit this file in the **same commit** so reviewers can't merge a status drift.
- When you discover a new launch-blocking item, add it to the top table.
- When you close one, leave it in the "Done" section with the commit hash that closed it — don't delete entries; history matters for the audit cycle.
- Don't trust this file blindly either: if a status feels stale, run the same evidence query against current code before acting on it. The point of this doc is to *replace* memory and chat recap, not to be a new memory to trust.
